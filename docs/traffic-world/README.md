# Traffic-management world: an affordable route to the vision

Status: proposed production plan. The user requested the broad urban traffic-management vision be reviewed/delegated while conserving tokens and cost. This does not claim the advanced systems or asset packs exist. It preserves the accepted persistent-city efficiency game and incremental delivery.

## Scope decisions

Treat maximum complexity/diversity as the long-term destination. The first deliverable should demonstrate one satisfying, measurable road improvement, not attempt every vehicle, road type and scenario at once. Reuse the approved fixed-camera city artwork, responsive interface, one currency, actual trip goals and saved towns. The current responder/debug work remains the immediate reliability priority.

A rich-looking traffic image is not proof of correct lane changes, bridge routing or bus capacity. Keep art, scenario configuration and simulation tasks separate so each can be verified without commissioning the others.

## Delivery order — revised by latest user direction

Routing mechanics and real debugging come first. **Mockups are removed. Scenario/asset variations come last.** This supersedes the earlier comparison-sheet-first production order.

1. Reproduce remaining player-reported service failures; prove arrival, work and return in saved cities.
2. Establish a shared routing snapshot and bounded congestion-aware route costs on current roads.
3. Add stable adaptive rerouting and an explicit emergency policy without overriding occupancy safety or trip goals.
4. Explain routing choices through the existing debugger and live overlays.
5. Validate one measurable mission/puzzle at equal offered demand using current tools.
6. Implement selected advanced road/vehicle mechanics before scenario and visual variations, which come last.

See [the routing plan](routing-plan.md) for jam acceptance gates, global-observer boundaries, tuning, events, module ownership and deferred features. One-way/roundabout, general multi-lane simulation, transit and grade separation remain dependency-driven later slices, not graphic-only upgrades.

## Deferred scenario ideas — not current deliverables

| Preset | Meaningful variable | Constraint |
|---|---|---|
| Morning rush | Demand concentrated toward a shared destination district | Explicit trip schedule/purpose; not merely a spawn multiplier |
| Evening rush | Reverse journeys and departure peaks | Trips return to real origins; do not silently swap goals |
| Weekend calm | Lower demand and a greater leisure share | Calm can be a valid enjoyable state |
| Festival overload | Temporary demand at a specified destination | Finite visitor capacity and a usable recovery route |
| Accident stress | Optional seeded incident timing/severity and affected road | No reward for casualties; never manufacture failure in every successful city |
| Optimized flow | Improved layout/control settings | Compare against the SAME demand and observation window |

Rush scheduling, festival demand and fault/construction events are proposals requiring configuration/model work. The current game should not pretend leisure traffic is commuting to work when a work-purpose system does not exist yet.

## No mockup work

Mockups and comparison sheets are removed from the plan entirely. Validate improvements in the actual game using live diagnostics and measured outcomes. Scenario and visual variations come last, after mechanics.
